# 变更记录 2026-10-03：主体判定 v3 + 入库补漏

承接同日的「归类时间轴」改造。这一轮解决的是**数据层**问题：为什么标题里明明写着公司名，素材还是被判"未识别"、还是散的。

## 一、根因：入库根本不写 region/entity

归类树是按 `category → region → entity` 三列分格的。但三条入库路径的 `INSERT` 里**都没有 region/entity 两列**：

| 入库路径 | 文件 | 原有列 | 缺什么 |
|---|---|---|---|
| 抓取（OpenClaw 文件） | `app/services/topic_parser.py` | 只有 `category` | region、entity |
| 手动录入 | `app/routers/topics.py` | 只有 `category` | region、entity |
| Codex 主编选题 | `app/services/operator_service.py` | **category 也没有** | category、region、entity |

后果：每次抓取进来的新素材 `region` 为空 → 不属于任何一个格子 → **在归类树里根本看不见**。当天入库的 11 条（#1624–1634）全部命中。

而"判定地区/主体"的逻辑只写在启动迁移里（跑一次就打标记），所以只有存量数据有标签，**新增数据永远是空的**。

## 二、改了什么

### 1. 三处入库同轮补列（`app/services/topic_parser.py`、`app/routers/topics.py`、`app/services/operator_service.py`）

入库时直接调用 `geo.judge(标题, 全文)`，与 `category` 同一次落定。判定规则就是「标题优先，标题认不出才读全文」。

### 2. 启动补漏闸（`scripts/init_db.py`）

每次启动扫一遍 `region` 或 `entity` 为空的行并补齐。理由是：入库是三条彼此独立的 INSERT，将来再加第四条（或有人直接写 SQL）照样会漏；版本迁移只处理存量，兜不住增量。

### 3. 判定规则带版本号（`app/geo.py` 的 `JUDGE_VERSION`）

原来每改一次判定就新造一个迁移标记（`tree_v1_migrated`、`geo_v2_migrated`）。改成 `JUDGE_VERSION` 常量：启动时比对 `system_settings.geo_judge_version`，不一致才全库重判。以后改词典只改这一处。

> 注意：版本升级会覆盖全表 `region/entity`。当前页面只读、没有人工修正入口，所以安全。**将来开放人工修正时，必须加"人工字段"标记并在重判时跳过**，否则用户改的会被启动迁移冲掉。

### 4. 主体词典补齐（`app/geo.py` 的 `COMPANY_REGION` / `GOV_REGION`）

这是"标题里有公司名却判未识别"的直接原因——**微软、谷歌、戴尔、思科、推特、小红书、哔哩哔哩、大疆、中兴**这些最常上新闻的主体，词典里根本没有。

- 公司：147 → 235 条
- 政府机构：35 → 55 条

同时纠正两处真实错判：`Stability AI`（在英国，原挂美国）、`Cohere`（在加拿大，原挂美国）。

### 5. 别称归并（`app/geo.py` 的 `ENTITY_ALIAS`）

补词典时发现：词典里 `Google` 和 `谷歌`、`Microsoft` 和 `微软` 是两条独立条目，落库会变成**两个格子**，同一条新闻线被拆两半——用户看到的"怎么是散的"有一部分就是这么来的。

新增 `ENTITY_ALIAS`（32 组），检测时两种写法都认，落库统一到规范名（美国公司用英文官方名，中国公司用中文名）。

## 六、遗留

1. **386 条仍判"未识别"**（24%）。多数是「多家公司对比」「纯中文标题无主体名」类，符合"宁可漏不可错"。若要继续降，得做中文实体抽取，不能靠加词。
2. **`ENTITY_ALIAS` 里 `理想`、`荣耀`、`联想` 等词有误伤风险**（如"理想情况下"）。这是词典法固有代价，词典里原有的 `苹果`（水果）、`小米`（粮食）、`滴滴`（拟声）也一样。命中错了在格子看得见，可以人工改。
3. 开放人工修正 `region/entity` 的入口时，必须同时做「重判跳过人工值」。
